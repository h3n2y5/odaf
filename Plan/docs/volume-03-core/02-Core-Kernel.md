# Chapter 02

# Core Kernel

---

# 1. Purpose

This chapter defines the Unified Runtime Kernel (URK) of the Oracle Dynamic Application Framework (ODAF).

The Unified Runtime Kernel is the execution core of the platform. It orchestrates metadata execution by coordinating runtime packages, execution contexts, platform services, and runtime engines.

The kernel does not execute design-time metadata directly. It operates exclusively on compiled Runtime Packages generated by the Metadata Compiler Infrastructure (MCI).

---

# 2. Design Objectives

The Unified Runtime Kernel SHALL:

- execute compiled runtime packages;
- orchestrate all runtime engines;
- isolate design-time from runtime execution;
- provide deterministic execution;
- manage execution contexts;
- coordinate platform services;
- remain independent of database implementation.

---

```text
Runtime Package

        ▼
Unified Runtime Kernel
        │
        ├── Context Manager
        ├── Service Registry
        ├── Object Graph Manager
        ├── Execution Dispatcher
        ├── Transaction Manager
        ├── Cache Manager
        ├── Event Dispatcher

                │

        ├── Dataset Engine
        ├── Workflow Engine
        ├── Rule Engine
        ├── Security Engine
        ├── Rendering Engine
        ├── Integration Engine
        └── Report Engine
```

The kernel SHALL orchestrate execution but SHALL NOT contain business logic.

---

# 4. Aggregate Root

The Aggregate Root is

```text
Unified Runtime Kernel
```

The kernel owns the execution lifecycle of every Runtime Package.

# 6. Kernel Responsibilities

The Unified Runtime Kernel is responsible for:

- loading Runtime Packages;
- initializing runtime services;
- resolving execution context;
- dispatching runtime requests;
- coordinating engine execution;
- collecting execution metrics;
- managing runtime lifecycle.

Business logic SHALL remain outside the kernel.

---

# 7. Kernel Lifecycle

Kernel initialization SHALL follow this sequence.

```text
Initialize

↓

Load Runtime Package

↓

Register Services

↓

Build Object Graph

↓

Warm Cache

↓

Ready

↓

Execute Requests

↓

Shutdown
```

Every stage SHALL complete successfully before the next stage begins.

---

# 8. Context Management

Each incoming request SHALL create a Runtime Context.

The Runtime Context SHALL contain:

- authenticated identity;
- security roles;
- tenant;
- organization;
- locale;
- time zone;
- transaction identifier;
- correlation identifier.

The Runtime Context SHALL be request-scoped and immutable.

---

# 9. Service Registry

The kernel SHALL maintain a centralized Service Registry.

Typical registered services include:

- Dataset Service;
- Workflow Service;
- Rule Service;
- Security Service;
- Rendering Service;
- Integration Service;
- Notification Service;
- Report Service.

All runtime services SHALL be resolved through the Service Registry.

---

# 10. Object Graph Management

The kernel SHALL execute Runtime Packages using an object graph.

```text
Application

↓

Module

↓

Feature

↓

View

↓

Dataset

↓

Workflow

↓

Rule
```

The object graph SHALL be immutable while executing a request.

---

# 11. Execution Pipeline

Runtime execution SHALL follow this pipeline.

```text
Request

↓

Resolve Context

↓

Resolve Service

↓

Navigate Object Graph

↓

Execute Engine

↓

Generate Response

↓

Audit

↓

Release Context
```

Execution SHALL remain deterministic.

---

# 12. Runtime Isolation

The Unified Runtime Kernel SHALL remain independent from physical implementations.

The kernel SHALL NOT directly depend upon:

- Oracle SQL;
- Oracle PL/SQL;
- database schema;
- physical storage.

The Runtime Package SHALL abstract these implementation details.

---

# 13. Stateless Execution

The kernel SHALL remain stateless.

State SHALL exist only within:

- Runtime Context;
- Runtime Package;
- Transaction Scope;
- Cache Policies.

No business state SHALL be stored inside the kernel.

---

# 14. Runtime Engine Coordination

The kernel SHALL orchestrate engine execution.

Typical execution order:

```text
Security

↓

Validation

↓

Workflow

↓

Dataset

↓

Integration

↓

Rendering

↓

Audit
```

The kernel MAY alter execution ordering according to compiler-generated execution graphs.

---

# 15. Constraints

| ID | Constraint |
|----|------------|
| KRN-001 | Kernel SHALL execute Runtime Packages only |
| KRN-002 | Runtime Context SHALL be immutable |
| KRN-003 | Kernel SHALL remain stateless |
| KRN-004 | Business logic SHALL NOT reside in the kernel |
| KRN-005 | Runtime execution SHALL be deterministic |

```text

↓
```

---

# 18. Risks

Potential risks include:

- oversized Runtime Packages;
- service registration failures;
- execution graph inconsistencies;
- cache corruption;
- non-deterministic execution.

These risks SHALL be mitigated through compiler validation, immutable Runtime Packages, service registration checks, runtime monitoring, and conformance verification.

---

# 19. Summary

The Unified Runtime Kernel is the execution heart of ODAF.

By separating execution orchestration from business logic, operating exclusively on immutable Runtime Packages, and coordinating all runtime engines through a centralized kernel, ODAF provides a deterministic, scalable, and technology-independent execution platform.

This kernel serves as the operational foundation upon which all higher-level platform services and business applications are built.
